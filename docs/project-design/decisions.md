# Design Decisions

The main choices behind the build, and why. Newest last.

## Initial plan

| # | Decision | Why | Instead of |
|---|----------|-----|------------|
| 1 | **Readings travel over MQTT through a broker** — the server's ingest service subscribes as its own client with its own certificate | Reuses the existing UART-to-MQTT bridge unchanged in shape; the server needs no inbound port for data, since it connects out to the broker | A self-hosted broker on the server (must expose and secure an MQTT port) · Bridge POSTing JSON over HTTP to an API on the server (drops MQTT, needs an open inbound port) |
| 2 | **Mosquitto locally, AWS IoT Core in the cloud** — same topics and TLS client certs; switching is config only | The whole pipeline can be built and tested without cloud resources or cost; same topics + TLS keep the switch small | IoT Core from the start (small cost, local setup depends on the cloud) |
| 3 | **Build and test locally first, cloud last** | Keeps cloud cost low; the first cloud deploy runs software already known to work | Infra early, develop against it (pays for idle resources, mixes app bugs with infra bugs) |
| 4 | **A local Multipass Ubuntu 24.04 VM mirrors the EC2 server** — one Ansible playbook for both | Same OS as the EC2 image, managed over the network the same way — the playbook is exercised locally before it touches EC2 | A container pretending to be the host (Docker-in-Docker is a weak copy of a server) · Only the compose stack locally (Ansible tested against EC2 only) |
| 5 | **Server stack: ingest → InfluxDB → Grafana in Docker Compose** | InfluxDB is built for time-series sensor data; Grafana gives a dashboard without a front end; Compose keeps each piece separate and replaceable | One container with SQLite + a simple web page (weaker dashboard, everything coupled) |
| 6 | **Ansible over SSH locally, over SSM on EC2** — only the inventory's connection settings differ | EC2 needs no open SSH port; access is controlled by IAM | SSH on EC2 restricted to one IP (open port, key to manage) · SSM on both (VM must register as a hybrid managed instance) |
| 7 | **Images built locally, pulled from ECR in the cloud** — CI builds + pushes, EC2 pulls by tag via its instance role | No cloud dependency while developing; in the cloud the server never builds, and runs exactly what CI produced | Building on EC2 (slower, build tools on the server, images can drift from what CI tested) |
| 8 | **Cloud infra in Python CDK** — IoT things/policies, EC2, EBS, ECR, CloudWatch | Versioned, reviewable, unit-testable, same language as the rest of the tooling | Creating resources by hand in the console (not repeatable) |
| 9 | **Separate repository** — shared code (register headers, UART and clock drivers) copied in | Different purpose and components from cloud-clock-scaling | Adding it to the cloud-clock-scaling repo (two unrelated devices in one history) |

## During the build

| # | Decision | Why | Instead of |
|---|----------|-----|------------|
| 10 | **SPI flash + store-and-forward moved to stretch** — no offline mode in the core build | The W25Q64 modules haven't been delivered, and nothing else in the pipeline depends on them. Readings taken while the link is down are lost | Waiting for the parts (blocks the project) · An SPI part on hand (74HC595, LCD) — neither can store readings |
| 11 | **SPI LCD as a stretch goal** — Axiometa 0.96" IPS LCD shows the latest reading | On hand; a readout on the device that needs no PC or server | 74HC595 driving LEDs (on/off states only, can't show readings) |
| 12 | **PC forwarder script locally, bridge swapped in before the cloud** — a Python script reads the Nucleo's USB COM port and publishes to Mosquitto; the Genesis Mini replaces it as the last local step | The local pipeline is built and debugged over a wired link, without Wi-Fi or bridge firmware in the way; the bridge is then one swap, tested locally before the cloud. The Nucleo has one USB COM port (USART2 via ST-LINK) — while the forwarder holds it, a serial terminal can't open it | Bridge from the start (Wi-Fi + a second firmware in every early debug step) · Readings to a serial monitor first, Docker later (an extra stage the forwarder replaces directly) |
| 13 | **Stay on Windows: stack in the Multipass VM, PC forwarder kept** | x86 Ubuntu 24.04 VM stays a close twin of EC2, with no reinstall or dual-boot setup. The cost is the forwarder script, since a container in the VM can't open the Windows COM port | Raspberry Pi 2 (32-bit ARM, 1 GB RAM, no InfluxDB 2 build, not a twin of x86 EC2) · Native Ubuntu via dual boot (container gets `/dev/ttyACM0` directly, no forwarder — but a new OS install first) |
| 14 | **Commands (`help` / `read` / `rate`) sent from Docker through Mosquitto** — the forwarder (later the bridge) is two-way: readings up, commands down | The command path is the same one the readings use, so it works in the finished product too, not only at the bench; the single USB COM port stays with the forwarder | A command line in a serial terminal (can't open the COM port while the forwarder holds it; bench-only) |
| 15 | **Polled UART on the Nucleo** — no receive interrupt or ring buffer | Readings go out on a timer; commands coming in are short and rare, so a polled line parser keeps up | Interrupt-driven receive into a ring buffer (needed for fast or constant incoming data, which this link doesn't have) |
| 16 | **Read-now button as a stretch goal** — a button press takes and sends a reading immediately, alongside the timed readings | Timed readings plus the `read` command already cover on-demand readings; a physical button pairs with the on-device LCD, which is also a stretch goal | Button in the core build |
| 17 | **SPI flash + store-and-forward back in the core build** (reverses #10) | The W25Q64 modules have arrived, so the reason for deferring is gone. Readings taken while the forwarder, bridge or broker is down are kept and replayed instead of lost | Leaving it as a stretch goal (gaps in the data whenever the link drops) |
| 18 | **Grafana on EC2 reached through SSM port forwarding** — `aws ssm start-session` tunnels EC2's port 3000 to `localhost:3000` | Same browser-to-port access as the local VM, with no public port, domain or TLS certificate to manage; reuses the SSM access already chosen for Ansible (#6) at no extra cost | nginx reverse proxy with public HTTPS (extra container, domain + certificate, open port 443) · SSH tunnel (needs port 22 open) |
| 19 | **Local VM stays a working deploy target after the cloud phase** — one config per environment (local / cloud) picks the broker, certificates and image source; the same playbook deploys to either | Changes can still be built and tested locally at no cost before they reach EC2, and the stack can run without AWS at all | Retiring the VM once EC2 is live (every later change tested against the cloud) |
| 20 | **Local is the primary environment; the cloud is a proof deployment** — one or a few deploys to AWS show the same stack runs there, but day-to-day running and development stay on the VM | Keeps AWS cost and cloud debugging time small while still proving the stack is cloud-ready | Running the system on EC2 long-term (ongoing cost, slower iteration) |
| 21 | **InfluxDB schema planned for queries, plus a downsampling task** — identifiers as tags (indexed), readings as fields; an InfluxDB task writes hourly averages to a separate bucket for long-range graphs | Grafana filters by tag, so those lookups use the index; long-range graphs read a few hourly points instead of every raw reading | Default schema with everything as fields (every filter scans all data) · Raw readings only (long-range graphs aggregate everything on each refresh) |
| 22 | **Compose stack run by a systemd unit** (`weather-stack.service`) | Starts at boot only after Docker and the data-disk mount are up; the whole stack is started, stopped and checked with `systemctl` like any other service | Per-container restart policies alone (no ordering against the disk mount, no single status for the stack) |
| 23 | **InfluxDB backups on a systemd timer** | `Persistent=true` runs a backup missed while the host was off; each run's output lands in the journal | cron (missed runs are skipped, output not in the journal by default) |
| 24 | **Container logs to journald** (Docker `journald` log driver) | Host and container logs in one place, read with `journalctl`; journald caps total log size, which covers log rotation | Default `json-file` driver with `max-size` set per container (logs split from the host's) |
| 25 | **Separate accounts with least privilege** — `deploy` for Ansible (SSH key only, sudo, every escalation logged); `weather` system user (no login) owns `/srv/weather` and runs the backup; root SSH login and password auth disabled | A compromised or buggy app process can only reach the `weather` user's files; admin access is key-only and audited | Everything as root or the default `ubuntu` user (one compromise reaches the whole host) |
| 26 | **Backups taken through InfluxDB's API with a token**, not `docker exec` | Keeps `weather` out of the `docker` group, which is effectively root (any member can mount the host disk into a container) | Adding `weather` to the `docker` group so it can exec into the container |
| 27 | **Minimal published ports, bound per environment** — only Grafana and Mosquitto publish ports; InfluxDB and ingest stay on the Compose network; on EC2 Grafana binds to `127.0.0.1` | Docker writes its own iptables rules that bypass ufw, so a published port is reachable whatever ufw says; not publishing (or binding to loopback) is what actually keeps a port closed. The SSM tunnel arrives on `localhost`, so loopback-only costs nothing on EC2 | Relying on ufw alone (silently bypassed by Docker) · Custom `DOCKER-USER` chain rules (more rules to maintain for the same result here) |
| 28 | **cloud-init bootstraps, Ansible configures** — one cloud-init file (used by Multipass and as EC2 user data) creates the `deploy` user and its SSH key at first boot; Ansible does everything else, on every run; the default `ubuntu` user is then locked | Ansible logs in the same way from its very first run; automation has its own account, so its actions are clear in the logs and its key can be revoked on its own; one less login to protect | Ansible's first run as `ubuntu` creating `deploy` (two login setups to manage) · Bootstrapping everything in cloud-init (runs once only, can't apply later changes) · Using `ubuntu` for Ansible (shared default account, same sudo power, no separation) |
| 29 | **Updates ship as a new image tag + a playbook re-run** — the tag is an Ansible variable; the re-run pulls the new image and restarts only the changed container; done by hand on the VM, automated in GitHub Actions for EC2 (build → push to ECR → playbook over SSM, AWS access via OIDC) | Every release goes through the same path that built the server, so the server never drifts from the playbook; the run report shows exactly what changed; untouched services keep running | Editing files or running `docker` commands on the server by hand (changes not recorded, server drifts) · Rebuilding the whole server for each change (slow, data disk handling every time) |
| 30 | **One release script for both environments** — `release.sh <env> <tag>` builds the image, stores it (local) or pushes it to ECR (cloud), then runs the playbook with that environment's inventory; GitHub Actions calls the same script for the cloud | The release path is tested locally before CI ever runs it; CI holds no deploy logic of its own, so local and cloud releases can't drift apart | Separate deploy steps written inside the GitHub Actions workflow (cloud path only testable by pushing) |
| 31 | **Store-and-forward driven by acknowledgements** — ingest publishes the last `seq` it wrote to InfluxDB; the forwarder / bridge passes it down the UART; the Nucleo keeps every reading in flash until its `seq` is acknowledged, frees a 4 KB sector once all its readings are acked, and resends anything unacked | Nothing is lost in the time it takes to notice an outage, and the ack only comes after the database write, so a broker, ingest or InfluxDB failure all look the same to the device. The bridge + Nucleo are treated as one device; the bridge needs no health logic of its own | A status / heartbeat topic with a timeout (readings sent during the timeout window are lost) · Broker connection state only (misses ingest or InfluxDB being down) |
| 32 | **Readings timestamped on the Nucleo by its RTC** — driven by the on-board 32.768 kHz LSE crystal (X2, fitted on the MB1136 C-04 board); the forwarder / bridge sends the real time down the UART on connect (bridge gets it via NTP); every reading carries its sample time | Readings replayed from flash keep their true time instead of the replay time; survives a Nucleo reboot once the time is set again | Each line carrying its age from the millisecond counter (lost on reboot with readings still in flash) · Bridge stamping on forward (replayed readings get the replay time) |
| 33 | **Reading line: `W,<seq>,<epoch>,<t_centi_C>,<p_Pa>,<rh_centi_pct>`** — integers only (temperature signed, in hundredths of °C; humidity in hundredths of %); ingest converts to decimals before writing | No floating-point maths or printing on the Nucleo; the scale is fixed by the protocol, so every reader converts the same way | Decimal text (`21.40`; float formatting on the MCU) · JSON (larger lines, parsing on the MCU) |
| 34 | **`seq` carries on across reboots** — on boot the Nucleo scans the flash log for the highest `seq`; a dedicated W25Q64 sector also holds the last `seq` used, for when the log is empty | A reused `seq` would collide with readings already acknowledged and break the ack and duplicate checks | Restarting `seq` at 0 on boot · Storing it in the MCU's internal flash (shares space with the firmware) |
| 35 | **Cumulative ack: `A,<seq>`** = every reading up to and including `seq` is stored; ingest only acks up to the last `seq` with no gap before it, so a missing reading is resent | One small line acknowledges many readings; a reading lost in transit can't be freed from flash by a later ack | One ack per reading (many more downlink messages) |
| 36 | **Time line `T,<epoch>`** sent down on every (re)connect and then hourly; after a power-up the Nucleo takes no readings until the first `T` has set its RTC | Every stored reading has a true time; the hourly resend corrects RTC drift. The only loss is readings while powered up with no link, which is rare | Readings marked "time unknown" (stored but unusable on a time axis) · Time sent once only (RTC drift builds up) |
| 37 | **Two timestamps per reading** — the Nucleo's sample time is the InfluxDB point time; ingest adds the server's arrival time as a field (`received_at`) | Graphs use when the reading was taken; arrival minus sample time shows delivery delay, marks which readings were replayed from flash, and exposes RTC drift | Sample time only (no view of delays or replays) · Arrival time only (replayed readings land at the wrong time) |
| 38 | **Commands and replies carry an ID** — `C,<id>,<command>` down, `R,<id>,ok` / `R,<id>,err <reason>` / `R,<id>,<text>` up | A reply can always be matched to its command, even when several are sent close together | Commands and replies with no ID (replies can't be told apart) |
| 39 | **`read` produces a normal `W` line** plus `R,<id>,ok` | An on-demand reading is stored, acked and graphed like any other; one code path for every reading | Reading returned only in the reply text (shown once, never stored) |
| 40 | **Genesis Mini (ESP32-S3) stays the Wi-Fi bridge** | Its `uart-mqtt-bridge` firmware already works and only needs the new line routing; the Nucleo keeps sending plain protocol lines | ESP32-C3 running Espressif's ESP-AT firmware (Nucleo would have to drive AT commands for Wi-Fi, MQTT and certificates) |
| 41 | **Deadman alert in the core build** — Grafana alerts when no reading has arrived for 5 minutes | Shows that data has stopped arriving from anywhere in the chain (Nucleo, link, broker or ingest), separately from the device's own store-and-forward | Leaving all alerting as a stretch goal (an outage goes unnoticed until someone looks at a graph) |
| 42 | **3.5" ILI9488 screen on the Nucleo, in the core build** (replaces #11) — shares the SPI bus with the W25Q64 (own chip select); shows the latest reading from Phase 3, then RTC time, link status and the flash backlog | Readings and device health are visible with no PC, network or server; the backlog view shows store-and-forward working. Added after the flash driver so the SPI bus is already proven | 0.96" Axiometa LCD as a stretch goal (#11; too small for the health view) · Driving it from the Genesis Mini (not on the Nucleo's SPI bus, and the bridge only arrives in Phase 8) · Screen first, before UART / I2C (a large driver before any reading exists) |
| 43 | **Hardware-in-the-loop test in CI** — a self-hosted GitHub Actions runner on the PC, with the Nucleo plugged in, flashes each new firmware build, sends commands over the COM port and checks the replies | Every firmware change is tested on the real board, not only compiled; catches driver and protocol breakage before it reaches the bench. The COM port is shared with the forwarder, so the test stops the forwarder while it runs | Build-only firmware CI (compiles but never runs on hardware) · Manual bench testing before each merge |
| 44 | **UART link at 115200 baud, 8N1, lines end in `\n`** (`\r\n` also accepted on receive) | Matches the existing bridge firmware's UART settings and line handling, so the bridge's serial side needs no change; accepting `\r\n` lets a serial terminal be used for bench tests | A lower baud rate such as 9600 (slower, and the bridge would need changing) |
| 45 | **One MQTT topic per line type, under `weather/<device>/`** — `readings`, `replies`, `acks`, `commands`; device ID `nucleo-01` | Each client's policy can allow only the topics it needs (the device publishes readings and replies and subscribes to acks and commands; ingest the reverse); the device ID in the topic leaves room for more devices | A single shared topic for every line (no per-topic permissions; every client receives everything) |
| 46 | **MQTT payload is the protocol line as-is** | The link only routes by the first letter and never parses or rebuilds a line, so the format is defined in one place and the forwarder and bridge stay small | JSON payloads (the link must parse each line and build JSON, and ingest must parse it back) |
| 47 | **QoS 1 on every topic** | The broker redelivers a message until it is acknowledged; a duplicate delivery is harmless because a reading with the same `seq` is written once | QoS 0 (a message can be dropped silently) · QoS 2 (not supported by AWS IoT Core) |
| 48 | **Staged how-to guide with one git tag per phase** — one page per phase in `docs/how-to/`, each linking to a tag (`phase-01`, `phase-02`, …) placed when that phase works; the README also has a short section for running the finished system | A reader can follow the build in order and browse, download or diff the codebase exactly as it was at each stage; tags have readable names and stay fixed | A guide to the finished system only (the build order can't be followed) · Linking raw commit hashes (unreadable names, no clear stage boundaries) |
| 49 | **Wi-Fi bridge is part of the cloud setup only; the PC forwarder is the permanent local link** (changes #12) — the bridge is still tested against the local broker first, as the first cloud step, before it is pointed at AWS IoT Core | A local run needs only the Nucleo, its modules and the software — no second board and no Wi-Fi; the bridge is still proven against a known-good local stack, so the first IoT Core connection isn't also the bridge's first test | Bridge replacing the forwarder in the local setup (#12; every local run needs the ESP32-S3 and Wi-Fi) |
| 50 | **Link UART chosen at build time by PlatformIO environment** — `local` uses USART2 (the ST-LINK USB COM port) for the forwarder, `cloud` uses USART1 for the bridge; all protocol code goes through one `LINK_PORT` setting | Both links stay supported side by side; switching is selecting an environment and flashing, with no source edits; the protocol code is identical for both | Editing the port in the source for each switch (error-prone, shows up as a code change) · Running the protocol on both UARTs at once (two senders of acks, time and commands to arbitrate) |
| 51 | **Ansible runs from WSL2 (Ubuntu 24.04) on the PC** — WSL is the control node; the Multipass VM and EC2 are the targets | Ansible's control node needs Linux. WSL mounts the Windows drive, so the playbook is run straight from the repo folder it is edited and committed in; it starts on demand with nothing to launch or manage; the control node stays the same when the target changes from the VM to EC2 | A second Multipass VM as the control node (repo must be mounted or copied in; another VM to start and log into) · Running Ansible inside the server VM (the server configures itself, which doesn't match how EC2 is reached) |
| 52 | **The Wi-Fi bridge is its own repository (`uart-mqtt-bridge`), built at a named tag with this project's config files** — this repo holds only the bridge's config + secrets headers and names the tag it was tested with | The bridge is general-purpose and passes lines through unchanged, so no bridge code belongs here; pinning a tag means later bridge changes can't break this project | Bridge firmware kept inside this repo (changes #40's "existing firmware extended"; a second firmware to maintain here) · A git submodule (not needed when only a config file is project-specific) |
| 53 | **The Wi-Fi bridge is the only link, from the first protocol test** (changes #12, #49, #50) — protocol lines always run on USART1 to the bridge; USART2 (the ST-LINK USB COM port) carries debug output only; no PC forwarder and no per-link firmware environments | The bridge is already built and tested, so it no longer adds an unproven firmware to early debugging. One link means one firmware build and one code path, tested the same way at the bench and in the cloud; the USB COM port stays free, so the Nucleo and the bridge can both be monitored while the link runs | PC forwarder locally, bridge for the cloud only (#49; a second link to write and maintain that does what the bridge already does) · Protocol on either UART chosen at build time (#50; two builds to keep working) · A container opening the serial port directly (serial handling inside the server stack; local differs from cloud) |
| 54 | **Until this project's own server stack exists, the bridge repository's test setup is the broker side** — its Multipass VM running Mosquitto (TLS + client certificates), its certificate and build / upload scripts, with `mosquitto_pub` / `mosquitto_sub` on the PC standing in for the server. Anything the bridge is missing is added in the bridge repository and released there | The protocol is tested end to end over MQTT from the first firmware phase, long before the ingest service exists; no second broker or certificate setup is written here for the same job; fixes found by driving the bridge with a real device land where every user of the bridge gets them | Building this project's Mosquitto first (server work pulled ahead of the firmware it serves, duplicating a setup that already exists) · Leaving MQTT out until the server stack is built (the protocol runs untested over the real link for several phases) · Patching bridge behaviour inside this repository (the two copies drift apart) |
| 55 | **Development machine is Ubuntu; Ansible runs on it directly** (changes #13, #51) — the stack still runs in a Multipass Ubuntu 24.04 VM as the local twin of EC2; the Ubuntu host is the Ansible control node for the VM and for hand-run deploys to EC2, and a GitHub Actions runner is the control node for automated cloud releases. Windows is not supported | The control node needs Linux, and a Linux host is one without a WSL layer between the repo and the playbook; the VM sits on the host's network with no Windows port forwarding in between. Keeping the VM, not running the stack on the host, gives Ansible a separate machine to configure, as it has with EC2 | Windows host with WSL as the control node (#51; an extra Linux layer, and port forwarding to reach the VM) · Running the stack straight on the Ubuntu host (the playbook would configure the machine it runs on, which is not how EC2 is reached; host and server settings mixed) |
| 56 | **All work goes through pull requests** — each PR opens with a description and a checklist of steps, which are ticked off as they are done; a PR can change, drop items or be closed unmerged. Nothing is committed straight to the main branch, apart from a small fix that was left out of a merged PR | Each change is reviewable as one unit, with its purpose, its steps and its diff in one place; the main branch only ever holds merged, working states | Committing straight to the main branch (no record of why a group of commits belongs together; half-finished work lands on the main branch) |
| 57 | **No step-by-step build guide and no per-phase git tags** (changes #48) — the README carries the instructions for running the finished system; the merged pull requests are the record of how it was built | A staged guide and frozen tags have to be kept correct every time earlier code changes; the pull requests already hold each step's description, checklist and diff without extra upkeep, and a reader who wants to run the system needs only the final instructions | One how-to page and one tag per phase (#48; a second description of the build to maintain alongside the pull requests) |
| 58 | **Peripherals are driven through the STM32Cube HAL** (changes part of #9) — UART, I2C, SPI and the RTC use ST's HAL; no register headers or hand-written drivers are copied in from cloud-clock-scaling | The HAL is ST's supported driver layer and what production STM32 firmware is normally built on; the same calls work across the STM32 family, so the firmware moves to another STM32 with pin and clock changes only, and the effort goes into the system itself (protocol, store-and-forward, server) | Hand-written register drivers (#9; every peripheral driver written and maintained here, tied to one chip) |
| 59 | **Nucleo firmware is built with PlatformIO on the STM32Cube framework** (`framework = stm32cube`) — clock, pin and peripheral setup is written by hand with HAL calls; STM32CubeMX is used only as a reference for clock and pin settings, never to generate the project. A small job may write a register directly, through the CMSIS device header that ships with the HAL | The bridge firmware is already built with PlatformIO, so both firmwares share one build tool, one set of commands and one CI setup; every file in the repository is hand-written, with no generated code to keep in step with a configurator | A project generated by STM32CubeMX, built with CMake or STM32CubeIDE (a second build system alongside the bridge's; large generated files in the repository) · Zephyr (its own driver model in place of HAL calls, and a large system to bring up before the first line is sent) |
| 60 | **Nucleo firmware lives in its own `firmware/` folder** — `platformio.ini`, `src/` and `include/` sit there, not at the top of the repository | The repository also holds the Ansible playbook, the Docker stack, the ingest service, the CDK code and the bridge config; a folder per part keeps each one's files and build output apart, and the top level shows the parts of the system at a glance | PlatformIO project at the top of the repository (firmware files mixed in with the server and infrastructure folders) |
| 61 | **System clock is the internal 16 MHz oscillator (HSI), with no PLL and no bus dividers** — set explicitly at start-up, though it matches the chip's state after reset | Nothing in the firmware needs more speed: a reading every few seconds, a 115200 baud UART, and I2C and SPI at modest rates. With no PLL there are no PLL factors or flash wait states to get right, the clock does not depend on any external part, and power use stays low | The PLL at up to 100 MHz (more setup and more power, for speed nothing here uses) · An external clock source (depends on how the board is fitted) |
| 62 | **Each firmware module has its own folder under `firmware/lib/`, holding its `.c` and `.h` together** — `src/` holds only `main.c` and `include/` only `board.h` (the pin assignments) | A module's source and header sit side by side and can be read, moved or reused as one unit; PlatformIO finds and builds each folder on its own, with nothing to list. It is the same shape as the bridge firmware's module folders, so both firmwares are laid out alike | All sources in `src/` and all headers in `include/` (a module's two files in different folders; `src/` grows into one long flat list) · The `Core/Inc` + `Core/Src` layout of an STM32CubeMX project (grouped by file type; this project is not generated by CubeMX) |
| 63 | **The UART code is two layers: a `uart` driver and a `link` module on top** — `uart` sets up a UART (clocks, pins, speed) and sends bytes, and knows nothing about lines; `link` carries protocol lines to the bridge and uses `uart` for the bytes | Each module has one job, and each function inside it one step, so a fault is looked for in one place. The driver is not tied to the bridge, so the debug UART uses the same code | One module that sets up the hardware and also carries the lines (two jobs in one place; the debug UART would need its own copy of the setup) |
| 64 | **The Nucleo runs a handshake with the bridge before it uses the link, and keeps checking the connection afterwards** — at start-up it sends `H,request` every second until the bridge answers `H,ack`, for as long as it takes; it also answers the bridge's own `H,request`. Once connected it checks every 20 s, and after 2 unanswered checks in a row it treats the connection as lost and goes back to asking every second. The handshake covers the UART connection only, not Wi-Fi or the broker | The Nucleo and the bridge are two boards joined by wires, either of which can restart or come loose on its own; the Nucleo depends on the bridge for everything it sends, so it establishes that the bridge is there first and notices when it goes. It waits without a time limit because nothing can be sent without the bridge | Sending without checking (lines go into a dead wire unnoticed) · A handshake at start-up only (a wire that comes loose later is never seen) · Giving up after a time limit (the Nucleo has nothing else to do without the link) |
| 65 | **Timings and other tunable values live in a config header, `firmware/include/config.h`, not in the code** — the handshake's retry interval, check interval and missed limit, and the LED's blink time | A value is changed in one known place without reading the code that uses it, and the code states what it does rather than how long it waits | Values written into the modules that use them (each change means finding the value in the code) |
| 66 | **The user LED (LD2) shows the link to the bridge** — it toggles every 200 ms while the Nucleo is trying to make the connection, and stays on once the connection is made | LD2 is the only LED on the board the firmware controls (the other two show the ST-LINK and power), and the connection to the bridge is the first thing that has to work, so it is what the one LED shows. A fast blink and a steady light are told apart at a glance | A slow blink for "connected" (harder to tell from "connecting" at a glance) · An external LED (not needed until there is a second state to show) |
